# PR 撰寫：高品質變更說明與風險評估

本技能產出結構嚴謹、高訊噪比的 Pull Request 內文。

## 核心鐵律與確認閘門

> [!IMPORTANT] 確認閘門（Approval Gate）
> - **預覽與核准**：PR 標題與內文必須先在對話中呈現供 CK 審閱。
> - **獨立確認**：未經 CK 個別明確確認，嚴禁自動 push 分支或向 GitHub 發起 PR。
> - **機密隔離**：審查 PR 內文與 diff，確保無任何金鑰、密碼或敏感資料。

## PR 內文標準模板

```markdown
## 變更摘要 (Summary)

<以最精簡的視覺圖表現：Mermaid 流程圖、元件樹、呼叫樹或核心偽代碼>

## 實證數據 (Evidence)

- **前 (Before):** <失敗測試輸出、既有行為截圖或日誌>
- **後 (After):** <通過之測試結果、全新行為截圖或日誌>

## 合併風險評估 (Merge Danger)

- **決策門類型 (Door):** <單向門 (One-way) 或 雙向門 (Two-way)>
  *(說明是否容易無痛復原或牽涉不可逆變更)*
- **爆炸半徑 (Blast Radius):** <極小 / 局部模組 / 全系統>
  *(評估對外部相依、效能、相容性之可能衝擊)*
```

## 執行流程

1. **萃取變更精髓**：以簡明視覺（Mermaid / 偽代碼 / 元件層級）呈現架構異動，避免冗長文字堆砌。
2. **附上客觀證據**：提供明確測試通過輸出與驗證前後對比。
3. **風險客觀定性**：誠實標記單向門或雙向門，評估潛在副作用。
4. **回報預覽**：展示 PR 草稿並等待 CK 核准後續操作。
